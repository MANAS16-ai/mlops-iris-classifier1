# DVC Remote Storage: Understanding the Stored Hashes

## DVC Remote Storage Structure

```text
C:\Users\Admin\dvc-remote-storage
│
└── files
    │
    └── md5
        │
        ├── 21
        │   └── d441a28bce4417276097df955afc50
        │
        └── 67
            └── 4c8c36bb7c4ba8d851dee9e6ee67af
```

## What Are These Two Files?

The long filenames are **MD5 content hashes** generated by DVC.

They are not random filenames. DVC stores data using a content-addressable storage system.

Example:

```text
iris_v1.csv
    ↓
Calculate MD5 Hash
    ↓
21d441a28bce4417276097df955afc50
    ↓
Store as:
files/md5/21/d441a28bce4417276097df955afc50
```

The first two characters of the hash become the directory name:

```text
21 / d441a28bce4417276097df955afc50
```

Similarly:

```text
67 / 4c8c36bb7c4ba8d851dee9e6ee67af
```

---

# What Do the Two Hashes Represent?

The presence of two hashes strongly indicates that DVC has stored **two different versions** of the dataset.

## Version 1

```text
Dataset: iris_v1.csv
Rows: 150
MD5: 21d441a28bce4417276097df955afc50
Size: 2928 bytes
```

## Version 2

```text
Dataset: iris_v1.csv
Rows: 170
MD5: 674c8c36bb7c4ba8d851dee9e6ee67af
Size: 4462 bytes
```

Because the dataset contents changed, the MD5 hash changed.

DVC can therefore distinguish between multiple versions of the same file even when the filename remains unchanged.

```text
iris_v1.csv
     │
     ▼
DVC calculates content hash
     │
     ├── Version 1
     │      ↓
     │  21d441a28bce4417276097df955afc50
     │
     └── Version 2
            ↓
        674c8c36bb7c4ba8d851dee9e6ee67af
```

# Complete Git + DVC Workflow Demonstrated

The experiment demonstrates the following workflow:

```text
                 ┌──────────────────────┐
                 │      Dataset         │
                 │    iris_v1.csv       │
                 └──────────┬───────────┘
                            │
                        dvc add
                            │
                            ▼
                 ┌──────────────────────┐
                 │     DVC Cache        │
                 │  Hashed Data Object  │
                 └──────────┬───────────┘
                            │
                        dvc push
                            │
                            ▼
                 ┌──────────────────────┐
                 │    DVC Remote        │
                 │  Local Storage       │
                 └──────────────────────┘


                 ┌──────────────────────┐
                 │    .dvc Metafile     │
                 │ MD5 + Size + Path    │
                 └──────────┬───────────┘
                            │
                         git add
                            │
                            ▼
                 ┌──────────────────────┐
                 │        Git           │
                 │  Version History     │
                 └──────────┬───────────┘
                            │
                        git push
                            │
                            ▼
                 ┌──────────────────────┐
                 │       GitHub         │
                 └──────────────────────┘
```

# Important Commands and Their Purpose

### DVC Commands

```bash
dvc --version
```

Display installed DVC version.

```bash
dvc init
```

Initialize DVC in a Git repository.

```bash
dvc add <file>
```

Track a dataset using DVC.

```bash
dvc push
```

Upload DVC objects to remote storage.

```bash
dvc checkout
```

Restore actual data corresponding to the current `.dvc` pointer.

```bash
dvc diff <commit_hash>
```

Compare DVC-tracked datasets between versions.

```bash
dvc remote add -d localremote <path>
```

Configure a default DVC remote.

---

git status

Upload commits to GitHub.

Display content from a specific Git commit.

# Conclusion

The experiment successfully demonstrates a complete **Git + DVC data versioning workflow**:

- DVC tracks dataset contents using content hashes.
- Git tracks lightweight `.dvc` metadata files.
- Multiple dataset versions can coexist in DVC storage.
- `dvc push` stores data independently from Git.
- `dvc checkout` restores historical versions on demand.
- The two MD5 hashes in the remote correspond to two distinct versions of `iris_v1.csv`.

This confirms that data versioning, remote storage, Git integration, and historical dataset recovery are all functioning correctly
